# BI Dictionary Integration — hooking the builder into BI's governance layer

**Status:** Phase 1 code landed (inert until first sync) · **Owner:** Alvaro · **Created:** 2026-07-09
**BI counterpart:** the `agent_column_dictionary` / `agent_table_dictionary` initiative (Slack thread with Galip + ron.madar.halevi)

---

## TL;DR

BI has shipped an automated "governance layer" — two BigQuery dictionary tables that document the verified SQL logic behind Guesty's curated analytics marts. This directly feeds the builder's single most effective anti-hallucination mechanism:

> **From our own CLAUDE.md:** *"Verified SQL examples are the strongest guardrail (~95%). Text rules like 'use spec column names' only work ~70%."*

The dictionaries are a supply of verified, BI-authored SQL. We integrate them as an **additive context layer** loaded on demand via a new `get_bi_table` tool — mirroring `get_company_spec()`. They **do not replace** our `specs/` (they cover zero of Salesforce/Zuora/HubSpot/Jira/AdminData/Modjo).

## The two tables (verified against live BQ, 2026-07-09)

Both live in `guesty-data.guesty_analytics`, both auto-generated by a **Dataplex Gemini documentation scan** (created 2026-04-19, last refreshed ~mid-May 2026 → **~8 weeks stale**).

### 1. `agent_table_dictionary` — macro layer (highest value)

8 rows = 8 tables, each carrying the **full build query**.

| Field | Type | Notes |
|---|---|---|
| `dataset_id`, `table_name` | STRING | table identity |
| `full_query` | STRING | **the complete ETL SQL that builds the table** (6K–60K chars) |
| `query_explanation` | STRING | plain-English summary |
| `table_grain` | STRING | e.g. "one row per account per day" — **filled for only 2/8** |
| `upstream_sources` | STRING | lineage (source tables) |
| `_debug_raw_response` | STRING | raw Gemini output (debug residue) |
| `last_updated` | TIMESTAMP | ~mid-May 2026 |

Covered tables: `guesty_analytics.accounts_summary` (48K-char query), `zendesk_analytics.tickets_clean` (60K), `ops_kpi.addons_mrr`, `performance.ndr`, `ops_kpi.new_cs_kpis_2026`, `zendesk_analytics.incoming_outgoing`, `marketing.leads_summary`, `csm.csm_churn_report`. **All 8 have a real full query.**

### 2. `agent_column_dictionary` — micro layer

783 rows = columns across **12 tables**, but **only 181 (23%) documented**.

| Field | Type | Notes |
|---|---|---|
| `dataset_id`, `table_name`, `column_name` | STRING | column identity |
| `description` | STRING | one-line meaning |
| `business_logic` | STRING | how the value is derived |
| `sql_snippet` | STRING | the isolated SQL expression for the column |
| `source_tables` | STRING | tables the column draws from |
| `_debug_raw_response` | STRING | debug residue |

Coverage is **inverse to our needs**: strong on product/zendesk reporting marts, thin on the core tables we lean on (`accounts_summary` 4/117 columns, `tickets_clean` 0/209). The table dict's full queries partly compensate.

**Relationship between the two:** all 8 `agent_table_dictionary` tables are a subset of the 12 in `agent_column_dictionary`. The 4 column-only tables: `product_gpo.performance_ranking_score_agg`, `product_gpo.performance_rankings_monthly`, `zendesk_analytics.reservations_report`, `zendesk_analytics.billing_invoices`.

## How it makes the builder more robust & reliable

Plugs into **Phase 2 (validate_data)** of the builder — the step where SQL is confirmed with the user before any nodes are built.

| Reliability failure mode | Today | With BI dictionaries |
|---|---|---|
| Hallucinated table/column names | hand-written specs (~95% where SQL exists) | BI-blessed `full_query` gives exact tables/columns for 8 core marts |
| Wrong business logic (churn/NDR definitions) | reverse-engineered | inherit BI's real definitions verbatim |
| Wrong joins / grain (double-counting) | `JOIN_MAP.md` (human-only, not loaded at runtime) | `upstream_sources` lineage + `table_grain` (partial) |
| Spec drift as BI evolves | discovered when a workflow breaks | `last_updated` staleness signal (if refresh is fixed) |
| Manual maintenance (Galip's sheet) | Alvaro + Galip by hand | BI's pipeline maintains it centrally |

## Integration design (Phase 1 — landed here)

Materialize → load on demand, mirroring `get_company_spec()`. Zero production impact until the first sync runs.

```
tools/sync_bi_dictionary.ts   reads both BQ dicts → writes specs/bi/<dataset>__<table>.md + _INDEX.md
chat-ui/src/lib/bi-dictionary.ts   filesystem reader: getBiTableKeys(), readBiTable(), listBiTables()
chat-ui/src/lib/claude.ts   registers get_bi_table tool ONLY when specs/bi/ is populated (empty ⇒ tool absent)
specs/  →  /app/knowledge/specs   (already mounted; specs/bi ships automatically)
```

Each generated `specs/bi/*.md` carries a **provenance header** (source table, `last_updated`, staleness warning) and a **hardcoded-literal guard** (flags snippets containing date literals like `'2025-12-31'` so the builder surfaces them for confirmation instead of copying blindly).

**Why materialized (not live BQ per chat):** preserves prompt caching, avoids per-request BQ latency, and the source data changes infrequently. Re-run the sync on a schedule (nightly/weekly) — ideally as an n8n workflow (dogfood).

## Gaps to raise with BI (governance)

1. **`agent_logs` doesn't exist yet** — the usage-tracking table is still aspirational. Co-design the schema; the builder is the right emitter (it already has SSO email + prompt + department + deploy status) rather than a per-analyst n8n snippet.
2. **No verification/provenance flag** — dicts are raw Dataplex-Gemini output (`_debug_raw_response` present). Ask for a `verified` / `reviewed_by` column so we can treat blessed rows as authoritative and the rest as hints. **Biggest governance gap.**
3. **Freshness SLA** — 8 weeks stale. Need refresh cadence + staleness signal.
4. **No curated join-key map** — joins are our worst error source (e.g. `zuora_analytics.invoices` joins via `mongo_account_id`, NOT `account_id`). Ask if a join map is on the roadmap.
5. **`table_grain` only 2/8 filled** — grain prevents fan-out double-counting.
6. **Coverage** — 12 tables, missing all non-covered source systems and thin on our core tables' columns.

## Reciprocal offer (the collaboration flywheel)

BI supplies **context in** (dictionaries); we supply **usage out**. Our `n8n_ops.executions` (155K executions) + the future `agent_logs` become the runtime half of BI's GenBI ROI dashboard.
